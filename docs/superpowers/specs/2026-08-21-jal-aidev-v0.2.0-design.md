# JAL-AIDEV v0.2.0 — Design Spec

Date: 2026-08-21
Author: Brian (lead) + Claude
Repo: https://github.com/JAL-Group/JAL-AIDEV (private)
Builds on: v0.1.0 (docs/superpowers/specs/2026-08-06-jal-aidev-design.md)

## 1. Goal

Upgrade JAL-AIDEV from a guardrails+scaffolder plugin into a full senior-engineering operating system for the JAL team: modular-monolith architecture enforced against spaghetti, polyglot (Go/Rust gRPC sidecars) under a strict Bun-only JS runtime, a FAANG/MANGO-grade agent hierarchy, a security red/blue suite, and a plain-language documentation website with study cases.

## 2. Constitution changes (jal-standards)

Add or tighten these rules in `skills/jal-standards/SKILL.md`:

- **Runtime:** Bun is the ONLY JavaScript/TypeScript runtime. Explicitly forbidden: node, deno, ts-node, tsx, nodemon, pm2-as-node. Bun is runtime AND package manager. (Vite/Next already forbidden.)
- **Polyglot:** Go and Rust are allowed ONLY as compiled gRPC sidecar services under `services/`, for CPU-bound or latency-critical hot paths, opt-in per project, and justified to Brian before adoption. They are services, never JS runtimes. The Bun/Hono app is always the primary and the contract owner (proto).
- **Architecture (mandatory):** Every backend is a modular monolith. Domain modules live under `apps/api/src/modules/<domain>/`. Each module exposes exactly one public surface (`index.ts`); other modules import only from that surface, never from a module's internal files. External infrastructure (Postgres, Redis, S3, AI) is reached through ports (interfaces) with adapters, not imported directly inside domain logic. Enforced by the boundary checker (section 6).
- **Monorepo (mandatory):** Every project is a Turborepo monorepo. No single-package projects.
- **Deploy:** The only permitted deploy target is Coolify at `deploy.jalgroup.id`. No other target may be configured.
- All v0.1.0 rules remain (frontend law, hardening, gpt-4o-mini default, icons, gradients).

## 3. Agent hierarchy (5 new, total 13)

Two-tier command structure mirroring FAANG/MANGO:

- **jal-principal** (NEW, HEAD): Principal-Engineer-grade assistant to Brian. Owns direction, architecture bar, scope, and the final quality gate. Talks to Brian, translates intent into a plan, and delegates execution to jal-lead and specialists (its sub-agents). Does not write bulk code itself; it decides, decomposes, and reviews. Senior, terse, on-point.
- **jal-lead** (existing): execution orchestrator under jal-principal. Runs the build/parallel-dispatch/gate/memory loop.
- **jal-systems** (NEW): senior Go/Rust systems engineer for gRPC sidecars. Perf-critical, memory-safe, benchmarked. Owns proto contracts on the service side.
- **jal-reviewer** (NEW): code-review gate agent. Correctness + boundary compliance + simplification, blocking on Critical/Important.
- **jal-redteam** (NEW): offensive security. Uses the installed hunt-* and bug-bounty skills to attack a JAL app and report exploitable findings.
- **jal-blueteam** (NEW): defensive security. Hardening, detection, log/audit review, closes the gaps red team finds.

Existing agents (jal-architect, jal-frontend, jal-backend, jal-security, jal-qa, jal-devops, jal-researcher) stay, updated to reference the new architecture + polyglot rules.

## 4. Skills (7 new)

Each is one focused `skills/jal-<name>/SKILL.md`, referencing jal-standards, senior/terse, no emdash:

- **jal-architecture** — the modular-monolith bible: module anatomy, the single-public-index rule, ports/adapters (hexagonal-lite), allowed dependency directions, folder-by-feature not by-layer, how to split a module, anti-spaghetti checklist.
- **jal-polyglot** — when to reach for Go/Rust (decision rubric: only CPU-bound/latency hot paths, benchmark first), proto-first contract, how the sidecar is wired, Docker + Coolify service, communication over gRPC.
- **jal-rpc** — Hono end-to-end typing: export `AppType`, typed `hono/client` in the frontend, no hand-written fetch types, keep the contract in one place.
- **jal-adr** — ADR/RFC discipline: when a change needs a design doc first, the template, numbering, where they live (docs/adr/).
- **jal-release** — changesets versioning workflow for the monorepo: add a changeset per change, version, changelog, tag.
- **jal-redteam-ops** — offensive workflow: scope, recon, the hunt-* skill map, exploit-or-disprove, evidence, responsible reporting to the team.
- **jal-blueteam-ops** — defensive workflow: hardening checklist beyond v0.1.0, detection/logging, triage of red-team findings, fix verification.

Update `skills/jal-security-hardening` to point to jal-redteam-ops + jal-blueteam-ops.

## 5. Commands (11 new)

Each `commands/jal-<name>.md`, frontmatter + terse senior instructions, `${CLAUDE_PLUGIN_ROOT}` and `$ARGUMENTS`/`$1`:

- `/jal-module <name>` — scaffold a compliant domain module (routes, service, repo, ports, public `index.ts`, tests) into `apps/api/src/modules/<name>/`; register it; run the boundary check.
- `/jal-service <name> <go|rust>` — scaffold a gRPC sidecar in `services/<name>/`: proto, server stub, Dockerfile, Coolify entry, and the Bun-side typed client; report the new tech to Brian in output.
- `/jal-migrate` — Postgres migrations: create/up/down over ordered SQL files in `migrations/` run by a tiny Bun runner. No ORM.
- `/jal-adr <title>` — create the next-numbered ADR in docs/adr/ from template.
- `/jal-ship <feature>` — the full senior loop: brainstorm -> spec -> plan -> parallel subagent build -> review gate -> memory. Invokes jal-principal.
- `/jal-pr` — run the review gate (jal-reviewer + /jal-review) then open a conventional-commit PR with the checklist; never force-merge.
- `/jal-deploy` — deploy to Coolify at `deploy.jalgroup.id` ONLY (hardcoded), tagged image, health check, one-command rollback to last stable tag. Refuse any other target.
- `/jal-debug <symptom>` — systematic debugging: reproduce, isolate, root-cause, failing test, fix, verify. No guess-patching.
- `/jal-audit` — deep scan: security (calls blue team), architecture drift (boundary checker), dependency audit, dead-code, bundle size; one report.
- `/jal-pentest` — red team + blue team run: jal-redteam attacks, jal-blueteam triages/fixes, single PASS/FAIL report with findings.
- `/jal-release` — changesets version + changelog + tag per jal-release.

## 6. Template upgrades (templates/monorepo)

Restructure to modular monolith and add the new tooling. Proof obligation: `bun install && bun run build && bun test && bun run check:boundaries` all pass.

- **apps/api restructure:** 
  - `src/modules/<domain>/` with one example module (e.g. `example/`): `routes.ts`, `service.ts`, `repo.ts`, `ports.ts`, `index.ts` (public surface, the only file other modules may import), `example.test.ts`.
  - `src/core/` for cross-cutting: hardening middleware, the port implementations (db/redis/s3/ai adapters), config wiring, the Hono app assembly that mounts modules and exports `AppType`.
  - Modules depend on core ports, never directly on pg/redis/s3 clients.
- **Boundary checker:** `tools/check-boundaries.ts` — a Bun script that builds the import graph of `apps/api/src` and fails (non-zero) if any file in `modules/A` imports from `modules/B/<not index>` or if a module imports another module at all except through its `index.ts`, or if a module imports a raw infra client instead of a port. Wired into: `package.json` script `check:boundaries`, CI, `/jal-review`, and a lightweight version in the guardrail hook.
- **Hono RPC:** api exports `AppType`; `apps/web` gets a typed `client.ts` using `hono/client`; one demo call replaces any hand-typed fetch.
- **Migrations:** `migrations/0001_init.sql` + `tools/migrate.ts` (up/down/create) + `package.json` scripts.
- **Changesets:** `.changeset/config.json` + README note.
- **Polyglot convention:** `services/README.md` documenting the gRPC sidecar layout and proto-first rule; `proto/` placeholder. Actual services generated by `/jal-service`.
- **ADR:** `docs/adr/0001-record-architecture-decisions.md`.
- Keep everything green from v0.1.0 (web build, api /health, QA stack).

## 7. Hook upgrades (hooks/guardrails.mjs)

Extend `evaluate()` (keep it pure + tested) to also block:
- `node`, `deno`, `ts-node`, `tsx`, `nodemon` appearing as a dependency or in a `package.json` script command.
- A deploy config (files matching coolify/deploy config) naming any host other than `deploy.jalgroup.id`.
- A cross-module deep import in `apps/*/src/modules/`: an import specifier reaching into `modules/<other>/<something-other-than-index>`.
- All existing blocks (emdash in frontend, vite/next/webpack/CRA) remain. New unit tests for each new rule.

## 8. Documentation website (docs-site/)

A plain-language docs website for using the plugin, with study cases. It is a JAL project, so it obeys the constitution: Bun-served static, no Vite, bento grid, modern minimalist, mobile app-like, no emdash, koboyo/reicon icons, feralui gradient only if needed.

- Location: `docs-site/` in the repo. Bun static build (`build.ts` via `Bun.build` for any JS) + a Hono static server (`server.ts`), or pure static HTML/CSS if no JS is needed. No framework beyond React-if-needed; keep it light.
- Audience: JAL teammates, plain language (mix of Indonesian and English is fine, but zero emdash), assume they are new to the plugin.
- Content:
  1. What JAL-AIDEV is and why (the condom metaphor made professional: it protects every project from spaghetti and drift).
  2. Install + per-project auto-enable (marketplace add, /plugin install, .claude/settings.json snippet).
  3. The constitution in plain words.
  4. The agent hierarchy (jal-principal down to specialists) with one line each.
  5. Every command with a one-line what + a copy-paste example.
  6. Study cases (walkthroughs), at least three:
     - Case A: "Build a SaaS dashboard from zero" using /jal-scaffold + /jal-module + /jal-ship.
     - Case B: "Add a Rust gRPC image-processing sidecar" using /jal-service rust + jal-systems.
     - Case C: "Ship a feature safely as a small team" using /jal-adr + /jal-ship + /jal-pr + /jal-deploy + rollback.
     - Optional Case D: "Security pass before launch" using /jal-audit + /jal-pentest.
  7. FAQ + troubleshooting (bun on PATH, private repo auth, boundary-check failures).
- Bento-grid landing + a simple sidebar or single-scroll layout, mobile app-shell. Diagrams via koboyo where they help (architecture, agent hierarchy).

## 9. Out of scope (v0.2.0)

## 10. Success criteria

1. Constitution updated; all 13 agents load and carry the new rules.
2. `/jal-scaffold demo` produces a modular-monolith monorepo where `bun install && bun run build && bun test && bun run check:boundaries` all pass, no Vite/Next/node.
3. Boundary checker fails on a deliberately planted cross-module deep import and passes on the clean tree.
4. Guardrail hook blocks: emdash-in-frontend, vite dep, node dep, a non-deploy.jalgroup.id deploy target, and a cross-module deep import; allows clean writes. New tests pass.
5. All 11 new commands present with valid frontmatter; /jal-deploy refuses non-jalgroup targets.
6. Hono RPC demo call is end-to-end typed; migration runner applies 0001_init.
7. Docs website builds and serves, contains all sections + at least 3 study cases, zero emdash, bento layout.
8. Plugin still installs from the private repo; v0.2.0 tagged.
